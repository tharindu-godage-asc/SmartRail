# SmartRail

SmartRail is a public railway passenger and operations platform (individual assessment, 29 Sep to 20 Oct 2026). It is an **information system, not a safety system**: it never controls trains or detects collisions.

## Stack
- Backend: .NET 10, modular monolith, feature folders, Clean Architecture (Domain, Application, Infrastructure, Api)
- Web (controller dashboard, platform displays): React
- Mobile (passenger app, operator app): Flutter, tested on an Android emulator
- Data: Postgres, EF Core migrations. Identity: Keycloak (ADR-08)
- Delivery: Docker, GitHub Actions, Argo CD on a local kind cluster (ADR-15). Environments as built:
  - `local`: Docker Compose on the owner's machine (`deployment_environment="local"`).
  - `dev`, `test`, `staging`, `prod`: one namespace each (`smartrail-<env>`) in the kind cluster, one Argo CD app each.
  - CI deploys every `main` build to dev, test and staging. Prod only changes through the manual `promote-prod` workflow plus a manual Argo CD sync. Details: `smartrail-platform/docs/workflows.md`.
- Identity: Keycloak in Compose only for now (not yet in the cluster).
- Observability: OpenTelemetry to Prometheus, Loki, Tempo, Grafana (Compose stack; the in-cluster collector forwards to it). Dashboard: SmartRail Overview.

## Commands
Run from `smartrail-platform/` unless noted.
- Build: `dotnet build -warnaserror`
- Test: `dotnet test`
- Run local stack: `docker compose up --build` (API on http://localhost:8080, Grafana on http://localhost:3000)
- Create or repair the cluster: `./scripts/bootstrap-cluster.sh` (Git Bash; safe to re-run)
- Database (EF Core, Postgres). Restore the pinned tool once: `dotnet tool restore`. The tool commands use `--project src/SmartRail.Infrastructure --startup-project src/SmartRail.Api`:
  - Add a migration: `dotnet ef migrations add <Name> --project src/SmartRail.Infrastructure --startup-project src/SmartRail.Api --output-dir Persistence/Migrations`
  - Apply to the Compose database: `dotnet ef database update --project src/SmartRail.Infrastructure --startup-project src/SmartRail.Api` (uses the admin connection from `SMARTRAIL_MIGRATIONS_CONNECTION`, default is the Compose admin user)
  - Print the SQL: `dotnet ef migrations script --project src/SmartRail.Infrastructure --startup-project src/SmartRail.Api -o migration.sql`
  - Undo the last migration (only if it is not applied or merged yet): `dotnet ef migrations remove --project src/SmartRail.Infrastructure --startup-project src/SmartRail.Api`
  - Never edit a merged migration; add a new one. Each slice adds its own tables in its own migration. A new table is usable by the API role automatically (default privileges); if it must be append-only or read-only, revoke explicitly in that migration and test it.
  - Two settings control the database at startup, both off by default: `Database:ApplyMigrationsOnStartup` (apply migrations as the admin user) and `Seeding:DemoData` (today's demo journey 8058). Docker Compose turns on the migrations (`Database__ApplyMigrationsOnStartup`); `Seeding__DemoData` is **off in Compose since 22 Oct 2026** (set it to `true` for the demo layer: journey 8058 for Nimal, 8070, and putting cleared reference services back); the cluster and prod never turn either on. With no `ConnectionStrings:Smartrail` the API runs without a database.
  - Reset the local database: `docker compose down -v`, then `docker compose up --build` (the init scripts in `docker/postgres/init/` run again).

- Identity (Keycloak, spec `_specs/02-keycloak-identity.md`). Compose runs Keycloak 26.7.5 in development mode: console http://localhost:8180 (user `admin`, password `admin-dev-only`), realm `smartrail`, database `keycloak`. Development-only passwords throughout.
  - The realm file `docker/keycloak/realm-smartrail.json` is the source of truth (roles, clients, demo users). It is imported only when the realm does not exist, so after editing it run `docker compose down -v` and `up`. The demo user IDs equal `DemoIds` in `Seeding/DemoIds.cs`; a test checks it.
  - Demo users: `nimal` (operator, assigned to the demo journey), `operator2` (operator, never assigned), `jayasinghe` (controller), and the `smartrail-caterer` client (client credentials).
  - Get a token: `scripts/get-token.sh nimal` (also `operator2`, `jayasinghe`, `caterer`). Example: `curl -H "Authorization: Bearer $(scripts/get-token.sh nimal)" http://localhost:8080/api/v1/whoami`. The `smartrail-dev-token` client behind it is Compose-only and must never be in another realm.
  - Check the real Keycloak by hand before merging identity changes: `scripts/smoke-auth.sh` (not in CI). The 403 cases are proved by the integration tests, which use their own test token issuer.
  - Export the live realm to compare with the file (the file is hand-kept and much smaller than an export): `docker compose exec -T keycloak /opt/keycloak/bin/kc.sh export --dir /tmp/export --realm smartrail --users realm_file --http-port=18080 --http-management-port=19000`, then `docker compose cp keycloak:/tmp/export/smartrail-realm.json .`. The extra ports avoid a clash with the running server.
  - **The issuer rule:** a token's `iss` is the address Keycloak was reached at. Compose fixes it with `KC_HOSTNAME=http://localhost:8180`, the API accepts only that issuer (`Authentication:Authority`), and fetches keys from `Authentication:MetadataAddress` (`http://keycloak:8080/...`, thanks to `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`). Always fetch tokens from `localhost:8180`. The Android emulator reaches the host as `10.0.2.2`; that is for the sign-in spike.
  - API settings (section `Authentication`): `Authority`, `Audience`, `MetadataAddress`, `RequireHttpsMetadata`, `ClockSkewSeconds` (30). With none set (the cluster today) protected endpoints answer 401 and public ones work; setting only some stops startup with "half configured". `Diagnostics:WhoAmI` (off by default, on in Compose) maps `GET /api/v1/whoami`.
  - **Secure by default:** every endpoint requires a signed-in user unless it is marked `.AllowAnonymous()`. The public list is `/api/v1/status`, `/health/live`, `/health/ready`, plus the five passenger reads `/api/v1/journeys/{journeyId}/status`, `/api/v1/trains/{trainNumber}/status`, `/api/v1/stations`, `/api/v1/trains` and `/api/v1/lines/{code}/status`; a test fails if anything else is anonymous. Policies `Operator`, `Controller`, `Caterer` come from the flat `roles` claim.

- Operator report and live status (slice 1, spec `_specs/03-operator-report-live-status.md`). Endpoints, all under `/api/v1/` and mapped **only when `ConnectionStrings:Smartrail` is set**, so the cluster (no database yet) does not have them:
  - `GET operator/journey` (role operator): the journey the operator is assigned to now, with stop IDs, scheduled UTC instants and `isArrivalStation` (true for every stop that has a scheduled arrival, so every stop but the first: spec 19 changed D-08 and FR-22; Arrived is optional, a departure never needs it); 404 when none.
  - `POST journeys/{journeyId}/events` (role operator): body `{ clientEventId, eventType: "Departed" | "Arrived" | "DelayReported", serviceStopId, occurredAt }` (spec 06). A stop report needs `serviceStopId` and nothing else. A **delay report** has no stop and needs `reason` (`SignalIssue`, `TechnicalFault`, `Obstruction`, `Weather`, `Unknown`) and exactly one of `totalDelayMinutes` (1 to 240, the TOTAL against the timetable, never added to the delay running) or `delayUnknown: true`; a total not greater than the delay in force is 409 `delay_not_greater` (after "unknown", equal to the last number is allowed). The reason is stored in the event payload and **never returned by any read** (D-10). "Unknown" sets `delayKnown: false` in the status read, with no estimated times and no `primaryEta`. No two reports of one journey may share an `occurredAt` (409 `order_conflict`). An arrival is accepted at any stop with a scheduled arrival, not at the first stop (422 `not_arrival_station`); an arrival at the final stop sets the journey `Completed`. 201 recorded, 200 repeat (same client event ID, or a different one for the same stop and time), 403 not assigned at `occurredAt`, 404 unknown journey, 409 conflict (journey Unassigned or Completed, same ID with different content, a second different time for a stop, impossible stop order, version conflict after 3 tries), 422 bad request or time outside the limits. The error body carries a stable `reason` code.
  - `GET journeys/{journeyId}/status` and `GET trains/{trainNumber}/status` (public). The train lookup returns the journey in progress (started, not Completed, not past its expected end plus the grace period), otherwise today's (even if Completed), otherwise 404 (rule R15; a night train stays visible after midnight). The status gains `actualArrival` per stop, `lastKnownPosition.state` ("Arrived" or "Departed") and `statusKey` `Completed`.
  - Settings (all have defaults): `Events:MaxFutureMinutes` (1), `Events:MaxAgeHours` (8), `Journeys:OnTimeToleranceMinutes` (2), `Journeys:VisibleAfterEndMinutes` (15, and it stays 15: a `Completed` journey leaves "in progress" by its status, spec 06 R11; 0 would hide a train that runs later than its last estimate).
  - Rules worth remembering: departure times must strictly increase with stop sequence; delay is rounded away from zero, then never negative; stop states are rebuilt from all events in occurrence order after every report; stop times are plain local times, so `ScheduleInstants` places stops after midnight on the next day (journeys up to 24 hours). Times are stored to the microsecond, so the handler trims incoming times to microseconds (a repeat must equal the stored value).
  - Try it on the Compose stack: `curl -H "Authorization: Bearer $(scripts/get-token.sh nimal)" http://localhost:8080/api/v1/operator/journey`, then POST a report with a time up to a minute ahead and up to 8 hours back; read it back with `curl http://localhost:8080/api/v1/trains/8058/status`.
  - Logging from a request or token: pass values through `LogSafe.Clean` (CodeQL flags log forging). Use typed values (GUIDs) where possible.
  - Integration tests: one fresh database per test (`JourneyApiTestBase`), the clock is a `FakeTimeProvider` you set per test, and each test clears its Npgsql pools (otherwise ~100 databases exhaust Postgres connections).

- Passenger reads (spec `_specs/04-passenger-find-trains.md`), all public, read-only, under `/api/v1/` and mapped **only when a database is configured** (so absent in the cluster today):
  - `GET stations`: the five stations in line order, **starting at Colombo Fort**, each with English, Sinhala and Tamil names and line sequences, plus `version`. `version` is also the `ETag`; `If-None-Match` with one tag, several, weak (`W/`) or `*` gets 304. `Cache-Control: no-cache`.
  - `GET trains?from=VYG&to=CF&date=2026-10-12`: trains between two stations (codes are case-insensitive: `CF`, `MDA`, `RGM`, `GPH`, `VYG`). `date` defaults to today and may be up to 7 days ahead (422 `date_out_of_range` otherwise). Each train has `atFrom.arrival`, `atFrom.departure` and `atTo.arrival` (each `scheduled` and `estimated`; `atFrom.arrival` is null at a service's first stop), `delayMinutes`, `statusGroup`, `statusKey`, `version`, `lastEventAt`. `live: false` means the answer is from the timetable (no journey yet) and the estimates, delay, version and `lastEventAt` are null. Errors: 404 `station_not_found`, 422 `invalid_request`, `same_station`, `invalid_date`, `date_out_of_range`. An empty list is a normal 200 answer (also for the opposite direction, because the seed has Inbound trains only).
  - `GET lines/MAIN/status`: `statusKey` `Normal` or `SomeDelayed`, `journeysInProgress`, `delayedJourneys`, `lastEventAt` (how fresh the data is) and `serverTime` (when computed; never show it as "updated"). No English text: the client words it, and with 0 journeys in progress says "No trains running now". `GET /api/v1/status` is unchanged.
  - `trains` and `lines` send `Cache-Control: public, max-age=5`: a deliberate approximation of OPS-10 (it bounds staleness, it does not invalidate on a version change).
  - Settings: `Search:MaxDaysAhead` (7), `Search:MaxResults` (50); the grace period is the one shared `Journeys:VisibleAfterEndMinutes`.
  - Which trains: live journeys not Completed, not over (expected end plus the grace period) and not yet departed From (a report at From or any later stop means it left); a service with no journey row for the date comes from the timetable (`runs_on` of Daily, Weekdays or Weekends; anything else is never offered and is logged); today's timetable-only trains only while the scheduled departure from From is not in the past. Holidays are not modelled.
  - **Not rate-limited.** NFR-13 (a Must) is deliberately deferred for every endpoint: no 429, no `Retry-After`. FR-11 (journeys generated 7 days ahead) is not built either, which is why future dates come from the timetable.

- Exceptions queue (slice B1, spec `_specs/07-exceptions-queue-controller-read.md`), controller role only, mapped only when a database is configured:
  - A delay report raises `ReasonAwaitingVerification` (Critical for TechnicalFault, Obstruction, Weather; High for SignalIssue, Unknown); a departure at least 30 seconds before its scheduled time raises `EarlyDeparture` (High). One report, one exception (unique `related_event_id` + `type`), saved in the same transaction as the event. The rules are `ExceptionPolicy` in Domain.
  - `GET /api/v1/exceptions?status=resolved`: the latest 50 closed exceptions, newest closure first, `{ items, total, limit }`, each with `resolvedAt`, `resolvedByName` (the user name stored at resolve time from the token's `preferred_username`, null for older rows), `resolution` and `secondsToResolve`. Rows are never deleted: resolving only sets `resolved_at`, `resolved_by`, `resolved_by_name` and `resolution`. The web app shows them on the Closed tab.
  - `GET /api/v1/exceptions?status=open` (Critical first, then oldest; 422 for any status other than `open` and `resolved`) returns `{ items, openCount }`, each item with `trainNumber`, `stationName` (null when nothing was reported yet), `type`, `severity`, `createdAt`, `ageSeconds`. `POST /api/v1/exceptions/{id}/resolve` with `{ action: "Acknowledged" | "NoActionNeeded" | "Escalated" }`: 204, 404 `exception_not_found`, 409 `already_resolved`, 422 `invalid_request`. Who resolved it is stored in `resolved_by` and logged.
  - `GET /api/v1/overview` (controller, slice B2): `{ openExceptionCount, journeys, serverTime }`. A journey is listed while it is running: **actually started** (its first stop report made it Running; a journey nobody has started is listed under `overdueToStart` instead, since 21 Oct 2026), not Completed, not past its expected end plus the grace period. Each has `statusKey`, `delayMinutes`, `delayKnown`, `lastEvent { type, stationName, occurredAt, source }`, `nextStop { stationName, expectedAt }` (null when nothing reported or the delay is unknown), `secondsSinceUpdate` (server clock, from when the report was received) and `verification` (`awaiting` when an open reason exception exists, else `none`). `source` is always `OperatorReport` today. Clients poll; nothing is pushed.
  - **Station displays** (spec 09, public, read only, mapped only with a database): `GET /api/v1/stations/{code}/board?platform=&count=` lists the trains that have not yet left the station (live journeys, else the timetable, same rules as the train search), sorted by expected time, each with `platform`, `arrival` and `departure` (`scheduled`, `estimated`), `state` (`Due` or `AtPlatform`), `delayMinutes`, `delayKnown`, `statusKey`, `lastSeen`, `live`. `next` (the next scheduled call today) and `firstTomorrow` (first call on the next day a service runs) are set when the list is empty. 404 `station_not_found`, 404 `platform_not_found`, 422 `invalid_request` (bad `count`; default `Board:DefaultCount` 8, maximum `Board:MaxCount` 20). `Cache-Control: public, max-age=5`. Counter `smartrail.board.reads` (panel "Station board reads"). The demo services plan platform 1 at every stop (migration `SeedPlannedPlatforms`); platform 2 is empty. Web: `/display/platform/:station/:platform` and `/display/board/:station` in `web/ops`, outside the sign-in, dark theme, three languages (Sinhala and Tamil wording is unverified except the phrases from the canvas). **They run as their own service**: `npm run build:display` builds a display-only bundle (no sign-in code) and `web/ops/Dockerfile.display` serves it with nginx; Compose service `display` on http://localhost:5174 (the API allows that origin). Delays are shown as hours and minutes (`4 h`, `1 h 05 min`). The platform display shows the first train big and the trains after it below as "Next trains" (it asks `?platform=P&count=6`; three rows at a time, paging upward every 8 s). **Demo trains:** 8075 is a night train in the reference data (22:10 Veyangoda, every day, platform 1); 8070 is created by the demo seeder at every API start in Compose (`Seeding:DemoData`) and leaves Veyangoda 4 minutes later (no journey, so boards show it from the timetable). The seed has three services; remember the daily 8075 when counting trains in tests.
  - **CORS** (spec 08): off unless `Cors:AllowedOrigins` is set (a list `Cors__AllowedOrigins__0`, or one comma-separated value). Exact origins only (startup fails on `*`, a path or a trailing slash); GET and POST; headers `Authorization` and `Content-Type`; no credentials. Compose sets `http://localhost:5173`; the cluster sets nothing, so nothing changes there. The overview journeys also carry `from` and `to` (first and last station names).
  - Not built: the operator flag (`OperatorCorrectionRequested`), backward and same-station conflicts. Metrics `smartrail.exceptions.raised` and `.resolved` (Grafana panel "Exceptions raised and resolved").

- **Verify a delay reason** (spec `_specs/16-controller-actions.md`, F2 only; F1 and F3 to F7 are not built), controller role: `POST /api/v1/exceptions/{id}/verify` `{ action: verify|change|reject, reasonCode }` and `POST /api/v1/exceptions/verify` `{ ids }` (up to 50, each on its own). Approved reasons: `SignalIssue`, `TechnicalFault`, `Obstruction`, `Weather` (`Unknown` is locked, must be changed). A verification is a `ReasonVerified` event; the public journey/train status then carries `reason { code, verifiedAt }` (absent until verified, D-10). Reject only closes the exception (`Rejected`). The open queue carries `reportedReason` and `canVerify`. Web: Exceptions screen; passenger app: live screen line "Verified by Operations".

- **Controller journey detail** (spec 16 F1, read only): `GET /api/v1/controller/journeys/{id}` (controller role) with stops and states, events with who made them, the reported and verified delay reason, the operator and the position as a place (never a prediction). Web `/journeys/:id` (one-track view with a text alternative, stops, events, Delay reason, Crew and control); the earlier crew page is now `/journeys/:id/crew`. The dashboard shell has a fixed frame (header and menu stay, the content and tables scroll).

- **API hardening** (20 Oct 2026): unhandled errors are a 500 problem answer with no details (`UseExceptionHandler` + `AddProblemDetails`); `/health` requests are filtered out of traces; the API description is served at `/openapi/v1.json` (anonymous, no data) **only when `OpenApi:Enabled` is true** (Compose sets it; off elsewhere, so the public-endpoint test is unchanged), with Swagger UI at `/swagger` (Swashbuckle UI package, a bearer scheme gives it an Authorize button; the UI middleware sits before authentication). HTTPS is not terminated by the app (the proxy or ingress does it), so there is no `UseHttpsRedirection`.

- **Platform assignment** (spec `_specs/20-platform-assignment.md`, spec 16 F4 reduced), controller role: `POST /api/v1/journeys/{id}/stops/{serviceStopId}/platform` `{ platformCode (null = back to planned), acknowledgeWarnings }`. The platform must be one of the stop's station (422 `platform_not_at_station`); a stop the train has left is 409 `stop_already_departed`; another train on that platform within `Scheduling:PlatformWarningMinutes` (10) is advice, 409 `warnings_not_acknowledged` with `warnings[]`, repeated with `acknowledgeWarnings` (never a block, FR-57). It writes `journey_stop_state.platform_id`, a `PlatformChanged` event (source Controller) and bumps the journey version in one transaction. Web: **Set platform** on the stops table of `/journeys/:id`. A train with no platform shows **TBA** on the main board and is on no platform display; the timetable wizard says so. Not built: the automatic Platform conflict exception.

- **Overdue to start** (21 Oct 2026): a journey that is Unassigned or Scheduled and whose first departure time passed by more than `Journeys:OverdueToStartMinutes` (default 5) is overdue (`OverdueRules`, information only). `GET /api/v1/assignments/journeys` items carry `overdueToStart`, and `filter=all` now also lists Completed and Cancelled journeys (the unassigned filter still does not); `GET /api/v1/overview` gains `overdueToStart[]` (`journeyId`, `trainNumber`, `from`, `to`, `scheduledDeparture`, `minutesLate`, `hasOperator`). Web: the Journeys page has status filters (Overdue to start, Not started yet, Ongoing, Completed, Cancelled) with counts and a train search; the Overview has an Overdue to start tile and table with Assign operator or Open journey.

- **Passenger app** (spec `_specs/10-passenger-app.md`, `mobile/passenger_app/`, README inside): Flutter, Riverpod, go_router, dio, shared_preferences; no account, state on the phone only. - **SmallBites and the food menu** (spec `_specs/11-catering-integration.md`, section 14): the caterer is its own system in `smallbites/` (.NET, own Dockerfile and tests, Compose service on http://localhost:8090; `/admin` marks items sold out, `/` is its stand-in website, `GET /api/menus/{station}` its API). - **Operator app Reports tab** (spec `_specs/12-operator-reports-and-history.md`, part 1 built): third tab, My reports from the phone queue (`ReportQueue.watchAll`), detail screens, delivered reports older than 7 days removed (`deleteDeliveredBefore`; waiting and rejected never). The demo seeder adds yesterday's finished 8058 for nimal.

- **Scheduling** (spec `_specs/13-scheduling.md`, S1 and S2 backend only), controller role, mapped with a database: `GET /api/v1/timetable/options?line=MAIN`, `GET /timetable/services?tab=weekly|extra|cancelled`, `GET /timetable/services/{id}`, `POST /timetable/validate` (always 200, `errors` and `warnings`), `POST /timetable/services` (body `kind` Weekly or Extra, `trainNumber`, `category`, `serviceType`, `days` + `effectiveFrom` or `dates`, `stops[]` with `stationCode`, `arrival`, `departure`, `platform`, `acknowledgeWarnings`): 201 with `journeysGenerated`, 422 `invalid_service` with `errors[]`, 409 `warnings_not_acknowledged`, 409 `train_number_in_use` (since 22 Oct 2026 any existing service, version or extra with that number refuses a create, whatever its dates; a change is an amend). Direction is derived from the stops. `train_service` has `kind`, `version`, `effective_from`, `effective_to`; a train number can have several rows (extra dates, later versions). `runs_on` is `Daily`, `Weekdays`, `Weekends` or `Mon,Wed,Fri`. `ServiceRuns.On` decides whether a service runs on a date; passenger reads use `ServiceRecord.RunsOnDate`. Generator: `Scheduling:GenerateJourneys` (off by default, on in Compose), `HorizonDays` 7, `GenerateEveryMinutes` 60; generated journeys are **Unassigned**. **Cancel and amend** (spec `_specs/14-scheduling-cancel-amend.md`): `POST /timetable/services/{id}/cancel` with `{ from, to (null = onward), reason }` cancels the train number on the line for those dates: journeys without events become `Cancelled` (`JourneyStatus.Cancelled`), all or none (409 `journey_has_events` with the date), a repeat is 200 with 0, 422 `nothing_to_cancel`, `invalid_reason`, `date_in_past`, `invalid_range`; the generator and `ServiceRuns.On(..., cancellations)` skip cancelled dates; a cancelled train is absent from search, board and status reads (404), not shown as Cancelled; the reason is for controllers only. `POST /timetable/services/{id}/amend` (body as create, weekly only, `effectiveFrom` tomorrow or later and after the current version's start) inserts version N+1, ends the old version the day before, re-points journeys that have not started (same journey id and assignment, fresh Pending stop states), cancels journeys of a removed day, and writes an `Amended` audit row whose `changes` feed the version `summary`; 422 `amend_extra_not_supported`, `identity_changed`, `effective_date_not_after_current`, `service_ended`. **Restore** (21 Oct 2026): `POST /timetable/cancellations/{cancellationId}/restore` closes the cancellation (`restored_at`, `restored_by`, change-log action `Restored`; the row stays) and returns its cancelled journeys to Unassigned or Scheduled; a service cancelled from today onward leaves the weekly list and shows under Cancelled with a Restore button; 404 `cancellation_not_found`, 409 `already_restored`. **Cancel one journey:** `POST /api/v1/journeys/{journeyId}/cancel` `{ reason }` (controller) is the service cancel for that journey's own date (same reason rule, same 409 `journey_has_events` and 422 errors, plus 404 `journey_not_found`); the journey page has a Cancel journey button (only while Unassigned or Scheduled) and the Cancelled tab can restore it. Not built: passenger notification, services that pass midnight.

- **Timetable screens** (spec `_specs/15-timetable-web.md`, W0 to W4 built, `web/ops/src/features/timetable/`): menu item **Timetable**, routes `/timetable` (tabs weekly, extra, cancelled), `/timetable/new`, `/timetable/extra/new`, `/timetable/:serviceId` (read only detail). The wizard keeps its draft in memory (`wizard/draft.ts`, `toRequest`), asks `POST /timetable/validate` on Review, shows errors beside the stop (`wizard/issues.ts`) and advice with a confirm box. `api.post` now returns the parsed body and `ApiError.body` keeps the problem details. The service detail has Cancel service (dialog) and Amend service (the wizard filled with the newest version, route `/timetable/:id/amend`). Not built: Playwright. Local note: the tokens test needs `npm run tokens` in a Windows checkout with CRLF.

- **Operator assignment** (spec `_specs/17-operator-assignment.md`, A1 backend; controller role, mapped with a database): `GET /api/v1/assignments/journeys?date=&filter=unassigned|all`, `GET /assignments/operators?journeyId=&from=&to=`, `GET /journeys/{id}/assignments`, `POST /journeys/{id}/assignments` (`operatorUserId`, `validFrom?` default 30 minutes before departure but not before now, `validTo?` null = until the journey ends, `acknowledgeOverlap`), `POST /journeys/{id}/assignments/{assignmentId}/end` (`reason` LostDevice, CrewChange or Other, `note?`). A new assignment from a time ends the covering one at that time (CrewChange); 409 `overlaps_later_assignment`, `operator_overlaps_another_journey` (**a block since 21 Oct 2026**: an operator on another live journey in that range cannot be assigned, `acknowledgeOverlap` is ignored; they are free when that journey gets another operator, their assignment is ended or it is cancelled or completed), `journey_not_assignable`, `already_ended`, `not_started`; 422 `operator_not_found`, `not_an_operator`, `operator_disabled`, `valid_to_not_after_from`, `valid_from_in_past_beyond_clock`. A report from an operator whose assignment was ended for **LostDevice** is refused (403 `assignment_ended`) when it is received at or after the end, whatever time it claims; other ends still accept a report made during the assignment. Ending does not change the stored journey status (see the spec's delivery notes). Operator names come from `Operators:Directory` in configuration (the demo operators) behind `IOperatorDirectory`; the Keycloak adapter (A3) is not built.

## Architecture rules
- Dependencies point inward: Api and Infrastructure may use Application; Application may use Domain; Domain uses nothing.
- One folder per feature (for example `Features/Reports/SubmitReport`) containing its endpoint, handler, validator and tests. Features do not reference each other's internals.
- Validate at the edge. Return RFC 9457 ProblemDetails for errors. No business logic in endpoints.
- Every external call goes through an interface in Application and an implementation in Infrastructure.
- Time comes from `TimeProvider`, never `DateTime.Now`.
- Every feature emits traces and metrics through OpenTelemetry with the `deployment.environment` attribute.

## .NET conventions
- `Directory.Build.props` sets `net10.0`, nullable, implicit usings and warnings as errors. Fix warnings; do not suppress them.
- Endpoints are minimal APIs: one `Map<Feature>` extension per feature (see `Features/Status/StatusEndpoint.cs`), registered in `Program.cs`. Prefer `TypedResults` for new endpoints, and put the route under `/api/v1/`.
- Use modern C#: primary constructors, collection expressions, records for DTOs and value objects, pattern matching. Seal classes that are not designed for inheritance.
- Pass `CancellationToken` through every async call from the endpoint down.
- Register services in each layer's own `DependencyInjection` extension; respect lifetimes (no scoped service captured by a singleton).
- Tests: xUnit. Unit tests for Application and Domain; integration tests use `WebApplicationFactory` against the Api project. Add Testcontainers once there is a real database.
- Packages are added per project with `dotnet add package` (no central package management yet).

## Product rules (do not break these)
- **Roles are fixed:** Passenger, Operator, Controller, Caterer, System Administrator. Never add a role.
- **Status is never colour alone.** Four status groups (normal, warning, unknown, disrupted), each with an icon and text.
- **Operators report only on their own assigned journey** (FR-03). Journey order is judged by occurrence time (FR-36).
- **Live updates target 30 seconds** from report to passenger screen (NFR-04). Offline and old data is labelled with the time it is from.
- **Scope decisions (12 Oct 2026):** food ordering is designed, not built (D-71). The passenger app shows the caterer's menu as a read-only list and a button to the caterer's website. SmartRail sends the caterer no train events (D-72). Do not build ordering, tokens, refunds or an outbox.
- Platform clashes are advice only, never blocking (FR-57).
- No hardware implementations.
